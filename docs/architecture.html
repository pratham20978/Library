MCP Hub · System Architecture

One endpoint, many governed integrations

An agent connects to a single URL — http://localhost:8000/mcp — and sees every enabled integration's tools namespaced as <integration>.<tool>. Behind that endpoint the hub authenticates, authorizes, confirms, rate-limits, sandboxes and audits each upstream MCP server. It reimplements none of them: every integration is a pointer to somebody else's official server. Four figures below: the topology, the gate sequence every call runs through, how a version is replaced without an outage, and who is allowed to change what.

Figure 01 · Topology

What runs where

One ASGI process serves both the MCP endpoint and the operator REST API, so a bearer token means the same thing to both. The gateway is the only place a tool call can be authorized. Everything to the right of the session pool is somebody else's code.

THE HEADLINE

The gateway is the only door

There is no per-integration URL and no second port. A tool call cannot reach an upstream without passing every gate in Figure 02, and no code path skips the audit write.

Three ways to reach an upstream

  • remote — proxied over HTTPS, nothing installed
  • subprocess — vendor code, env-allowlisted
  • container — required for community code

Where it degrades

No Redis means process-local locks and rate limits — correct for one replica, wrong for two. A dead upstream returns integration_unavailable for that integration only; everything else keeps serving.

Figure 02 · Request path

Eight gates, each of which can stop the call

The order is the contract. A denial short-circuits, so an expensive check never runs for a refused call, and rate limits are charged last so a probing agent cannot burn a legitimate user's quota on tools it has no access to. Every code on the right is a stable identifier an agent can branch on.

CLOSED BY DEFAULT

A non-empty allowlist is a closed one

Under selective exposure, a tool an upstream added yesterday is not exposed today. An empty allow list means "no allowlist configured, fall through" — never "allow nothing".

Four independent confirm triggers

  • per-tool policy decision: confirm
  • require_confirmation list
  • risk at or above the threshold
  • a verb in the manifest

Failures become results

A hub error comes back as is_error with a machine-readable code, not a dropped connection. The agent can route around one broken integration and keep using the rest.

Figure 03 · Update & rollback

Nothing is ever updated in place

A new version installs into its own directory and proves it can start and list tools while the current one keeps serving. Only then is current repointed by an atomic rename. That is why rollback is a rename back, not a re-download — it works with the network down.

BLAST RADIUS

Rolling, per integration

A failed GitHub update rolls back GitHub. Jira, Figma and everything else keep serving throughout. The hub never goes offline because one integration is updating.

Remote servers skip most of this

Jira, Figma and Notion are operated by their vendors. An "update" for them is a health probe plus a tool rediscovery — there is no artifact to stage.

Read the tool diff

If an upstream adds or renames tools, the lock file's digest changes and the hub logs it. A new upstream tool is not exposed until you allow it — review policies.yaml when that happens.

Figure 04 · Ownership

What to touch, and what to leave alone

Configuration is split by who owns it. Three files answer three different questions, and only two of them are yours to edit. The agent column is deliberately empty: an agent can call tools and read status, and that is the whole of it.

Dropping a manifest into config/manifests/ registers an integration. Adding it to integrations.yaml turns it on. The lock file records what actually happened — write to it by hand and you have lied to the update manager.

THINGS THAT DO NOT EXIST, ON PURPOSE

Deliberate absences

  • No hub.execute_shell or hub.execute_python — no arbitrary code execution tool of any kind
  • No API, CLI command, MCP tool or log line that returns a stored credential
  • No --value flag on secrets set — it would land in shell history and the process table
  • No Docker socket mount in compose — that is root on the host
  • No SSE fallback, no second port, no per-integration URL

BEFORE YOU CHANGE ANYTHING

Safe order of operations

  • mcp-hub doctor — environment, config and every integration in one pass
  • mcp-hub update --all --dry-run — resolves versions, changes nothing
  • Use --config-dir / --runtime-dir to rehearse against a scratch directory
  • disable before remove — it is the reversible move
  • After any update that changed a tool digest, re-read policies.yaml
